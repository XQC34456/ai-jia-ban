# AI 家办产品正轨重构计划书

从"财报生成器"回到"长期家庭财富 AI 顾问"

版本：V1.0 ｜ 正式产品开发基线 ｜ 核心原则：先校正主线，再扩功能

一、执行摘要

本计划不是一次 UI 优化，也不是继续堆图表、堆 Agent 工具或堆功能。目标是把 AI 家办从"能生成一份漂亮财务报告的产品"，重新拉回"能够理解用户问题、结合家庭财务档案进行推理、必要时主动追问、给出可执行建议，并长期记住和持续管理家庭财富的 AI 顾问"。

当前内测已经形成较好的工程基础：财富数据模型、Engine 确定性计算、结构化 Advisor、图表证据、行动计划、失效提醒、产品事件埋点等均已存在。但真实用户路径暴露出核心断层：顾问经常优先处理建档而不是问题；跨页面进入顾问后上下文没有真正被消费；取消建档可能导致原问题丢失；已有数据可能被重复询问；遇到不明确问题时没有形成"澄清—引导—回答"的顾问式循环。

因此，下一阶段不以"增加多少功能"为 KPI，而以"顾问是否真的像一个可靠的家庭财富顾问"为第一验收标准。

二、产品重新定义：我们到底在做什么

一句话定位：

AI 家办不是"AI + 财务报表"，而是一个拥有家庭财富档案、确定性财富计算能力、长期记忆和持续行动能力的 AI 家庭财富顾问。

| 层级 | 解决的问题 | 产品表现 |
|------|-----------|----------|
| 理解 | 用户现在到底想问什么？ | 识别问题、上下文、已有数据和缺失信息，不急于建档 |
| 推理 | 基于家庭真实情况应该怎么看？ | 调用 Engine / Decision / Scenario 进行确定性分析 |
| 沟通 | 用户需要什么答案？ | 直接回答；信息不足时只追问必要问题；不答非所问 |
| 行动 | 知道以后下一步怎么办？ | 建议、模拟、行动计划、采纳、完成 |
| 长期管理 | 下个月为什么还回来？ | 变化检测、失效提醒、重新评估、持续顾问关系 |
| 可视化 | 复杂判断如何一眼看懂？ | 图表和财报作为证据层，而不是产品主角 |

三、与 DeepSeek 等通用 Agent 的竞争策略

不应试图在"聊天模型本身"上击败 DeepSeek。目标是：同一个理财问题直接问 DeepSeek，AI 家办至少能给出同等水平的基础答案；而当用户建立家庭档案后，AI 家办进一步拥有家庭数据、确定性计算、历史变化和持续行动能力。

| 能力 | 通用 Agent | AI 家办目标 |
|------|-----------|------------|
| 通用理财知识 | 强 | 至少达到可接受的同等水平 |
| 当前问题回答 | 强 | 直接回答，不被建档流程打断 |
| 家庭数据 | 通常没有 | 结构化家庭财富档案 |
| 数字可信度 | 文本生成 | Engine 确定性计算 + 字段路径可追溯 |
| 情景分析 | 可回答 | 结合真实家庭数据计算并可视化 |
| 长期记忆 | 有限/依赖会话 | 家庭档案 + 历史事件 + 行动计划 |
| 主动管理 | 弱 | 失效检测 → 提醒 → 重新评估 |
| 行动闭环 | 通常停在建议 | 建议 → 采纳 → 计划 → 完成 → 再评估 |
| 财报/可视化 | 可生成 | 真实家庭数据自动生成证据层 |

四、当前产品必须纠正的核心问题

1. 顾问优先生成财报，而不是优先解决用户问题。
2. 建档流程与问答流程耦合：用户只是想问一个问题，却可能先被要求完整建档。
3. 跨页面进入顾问时，系统虽然可以预填问题，但回答链路没有真正消费上下文。
4. 用户取消建档后，原始问题没有成为继续回答的输入，导致"取消建档 = 问题被中断"。
5. 已经存在于家庭档案的数据没有被优先复用，容易重复询问和重复建档。
6. 面对不明确问题时，系统没有形成"澄清问题 → 引导用户 → 再判断"的顾问式对话。
7. 顾问工具调用如果由 LLM 自由决定，关键证据会出现不稳定；P1.1 已解决主要矛盾基线，但该原则需要继续扩展。
8. 财报、图表、评分、风险卡是结果和证据，不应反过来主导顾问行为。

> 核对结论（逐条裁定见 [verification-v10-current-state.md](verification-v10-current-state.md)）：**#1/#2/#3/#5 为真缺口，#4/#6 部分成立，#7 已由 P1.1 缓解但需扩展，#8 实际不成立（顾问已结论先行），不列入修复范围。**

五、新的核心交互原则

1. **先回答，再建档**：问题本身具有独立价值。能回答就先回答；需要家庭数据才能个性化时，再明确说明缺什么。
2. **问题永不丢失**：任何页面进入顾问、建档取消、澄清失败，都必须保留原始问题和上下文。
3. **建档是渐进式的**：边问边建、边用边完善，而不是一次性填写完整档案。
4. **不重复问已知信息**：先查档案、最近对话和当前上下文，只追问真正缺失且影响答案的数据。
5. **不懂就问**：低置信度、歧义或信息不足时，提出最小澄清问题，而不是硬答。
6. **先判断，再展示**：先形成观点和结论，再决定需要哪些图表、财报或证据块。
7. **数字必须可追溯**：关键数字来自确定性 Engine / Decision；LLM 不创造财务事实。
8. **建议必须能行动**：重要建议尽可能连接模拟、行动计划、采纳和后续复评。
9. **长期价值来自变化**：收入、负债、资产、目标或环境变化时，识别旧结论是否失效。

六、目标顾问架构：从"单轮回答"升级为"顾问循环"

Advisor 应明确拆成六个阶段。LLM 不是整个顾问，而是其中的理解与叙事组件。

| 阶段 | 系统职责 | LLM 职责 | 失败策略 |
|------|----------|----------|----------|
| 1. Intent | 识别用户真正目的 | 辅助语义理解 | 低置信度 → 澄清 |
| 2. Context | 读取档案、页面上下文、历史问题 | 理解语境 | 已有数据优先复用 |
| 3. Evidence | 确定必须取哪些 Engine 数据 | 决定解释方式 | 系统保证必需证据 |
| 4. Reasoning | Scenario / Decision / Engine 计算 | 形成顾问式判断 | 计算失败不得编造 |
| 5. Response | 校验结构与事实 | 直接回答、解释、追问 | 答非所问检测 |
| 6. Action | 连接模拟、计划、提醒、复评 | 提出下一步 | 不强迫行动 |

七、最关键的流程重构：问答与建档彻底解耦

例如用户说："我想投资 30 万。"系统不应默认理解成"我要建档"。正确流程应该是：

1. 识别用户意图：可能是在询问如何投资，也可能是在告知一笔资产计划。
2. 先给基础回答：说明流动性、风险、家庭负债、目标期限等关键判断框架，并说明可结合家庭情况进一步个性化。
3. 检查现有档案：已有收入、负债、现金、目标等数据直接使用，不重复建档。
4. 只追问影响决策的缺失项，例如"这 30 万是备用金之外的钱吗？"。
5. 用户愿意建档则边回答边沉淀；用户取消建档仍继续回答原问题。
6. 回答完成后，根据问题价值自然提供下一步：模拟、配置、行动计划或进一步评估。

八、跨页面顾问入口必须升级为"上下文入口"

Goals、Retirement、Allocation、Sandbox、Overview 等页面的"问顾问"不能只是跳转或复制文字，而应形成结构化 AdvisorContext。

| 来源页面 | 必须携带 | 顾问第一轮应该做什么 |
|----------|----------|----------------------|
| Goals | 目标、金额、已备、缺口、月存需求、期限 | 直接回答"这个目标怎么完成" |
| Retirement | 退休年龄、需求现值、可投资资产、缺口 | 解释缺口与关键变量 |
| Allocation | 当前资产结构、目标结构、集中度、风险指标 | 解释为什么这样配置/哪里需调整 |
| Sandbox | 方案参数、baseline、option、delta | 解释该情景对家庭的影响 |
| Overview | 关键指标、主要矛盾、近期变化 | 回答当前最值得关注什么 |

九、顾问质量正式验收标准

| 指标 | 验收标准 |
|------|----------|
| 相关性 | 第一段就回答用户真正问题，不先输出无关产品信息 |
| 澄清能力 | 不理解时提出最小必要澄清问题 |
| 数据复用 | 已有档案自动复用，不重复要求建档 |
| 取消建档 | 用户取消后仍继续回答原始问题 |
| 数字一致性 | 关键数字来自 Engine / Decision，与页面一致 |
| 个性化 | 有档案时利用家庭具体情况；无档案时仍能给有效通用回答 |
| 行动性 | 适合的问题能落到模拟、建议或行动计划 |
| 上下文连续性 | 跨页面进入后，第一轮回答与入口问题一致 |
| 长期性 | 后续数据变化能触发重新评估 |

十、正式开发路线

| 阶段 | 目标 | 核心工作 | 完成标志 |
|------|------|----------|----------|
| Phase 0 | 冻结主线 | Advisor-first、问答/建档解耦、数据复用 | 后续开发按同一主线验收 |
| Phase 1 | 顾问核心重构 | Intent/Context/Clarify/Answer/Action 状态机；问题不丢失；取消建档继续回答 | 核心真实问题通过 |
| Phase 2 | 家庭数据智能复用 | 档案查询、增量建档、字段冲突、来源追踪、缺数检测 | 不重复问；一句话持续完善档案 |
| Phase 3 | 顾问推理层 | 统一 Advisor → Engine → Scenario → Decision 编排；必需证据确定性预取 | 数字稳定 |
| Phase 4 | 建议与行动 | 建议、模拟、行动计划、采纳、完成、复评 | 关键问题形成闭环 |
| Phase 5 | 长期顾问 | stale、变化检测、主动提醒、重新评估、历史比较 | 用户有二次回来理由 |
| Phase 6 | 可视化证据层 | 根据回答动态挂载图表/财报/字段证据 | 图表服务答案 |
| Phase 7 | 商业化 | 核心价值稳定后再优化 Free/VIP | 不牺牲回答质量换转化 |
| Phase 8 | 对标验证 | 固定 12 项 prompt，与 DeepSeek 等盲测 + rubric | 基础回答接近；可追溯/长期管理领先 |

十一、第一批真实问题 Benchmark

1. 我有 30 万现金，现在适不适合投资？
2. 我想把 30 万投入股票，应该怎么分？
3. 我该提前还车贷还是拿钱投资？
4. 如果收入下降 20%，我能撑多久？
5. 这个孩子教育金目标怎么完成？
6. 按现在的情况，我退休够不够？
7. 我最近感觉钱越来越不够用了，怎么办？
8. 我应该买什么基金？
9. 我想买房，应该先还贷还是留现金？
10. 我不想建档了，你先回答我的问题。
11. 我之前已经告诉过你收入了，为什么又问？
12. 从目标页点"问顾问"后，顾问必须直接回答该目标问题。

每题至少记录：intent、是否正确理解、是否直接回答、是否需要澄清、确定性工具、关键数字、证据路径、行动建议。

十二、工程实施原则

1. 先写契约与测试，再改实现。关键顾问路径先建立回归用例。
2. 业务事实不由 LLM 计算；LLM 负责理解、解释、组织语言。
3. 系统层决定必需证据，LLM 不得通过自由选工具决定关键数字是否出现。
4. 前端上下文结构化传递，不依赖剪贴板、自然语言猜测或单纯页面跳转。
5. 统一模块契约：AdvisorContext、FinancialProfile、EngineResult、Recommendation、ActionPlan。
6. 每次修改通过单测、API、DOM/Playwright、真实手机验证；关键问题增加人工质量评审。
7. 不为了"看起来智能"增加动画、图表或按钮。每个功能必须提高理解、判断或行动。
8. 每个阶段独立提交，提交信息对应产品能力。

十三、暂缓事项

1. 大规模 UI 重设计与导航重做。
2. 继续增加大量图表类型。
3. 复杂 Dashboard / 数据看板。
4. 新的 Agent 数量扩张。
5. 复杂 VIP 转化玩法。
6. 正式 DeepSeek 对标报告。

原因：如果顾问核心逻辑仍然答非所问，任何新增功能都会把错误主线包装得更漂亮。

十四、项目成功定义

用户最终应形成稳定认知：

"我有任何家庭财富问题，都可以先问 AI 家办。它知道我的家庭情况；不知道时会问我；不会乱编数字；能告诉我为什么；能帮我比较方案；可以把建议变成行动；以后情况变了，它还会提醒我重新评估。"

最终壁垒不是"比 DeepSeek 更会聊天"，而是：

通用模型回答能力 × 家庭财富结构化数据 × 确定性财富 Engine × 可追溯证据 × 长期记忆 × 持续行动闭环。

十五、下一步：只做一件事

第一阶段不继续做 UI，不继续堆图表，也不先做 VIP。下一步先建立 Advisor Benchmark + AdvisorContext 契约，并从最典型的"跨页面问顾问"和"取消建档后继续回答"两条路径开始重构。

验收不是"代码完成"，而是完整链路跑通：用户提出问题 → 顾问理解 → 直接回答 → 必要时澄清 → 复用已有数据 → 需要时增量建档 → 个性化判断 → 可视化证据 → 行动计划 → 后续变化触发复评。

—— 本计划书结束 ——
